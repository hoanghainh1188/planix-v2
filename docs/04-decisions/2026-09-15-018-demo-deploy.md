# Môi trường demo: Render (free) + Neon (free) + hộp thư bắt email
- Ngày: 2026-09-15
- Feature liên quan: `018-demo-deploy` (issue #18) — điền mục "## Deploy" của `CLAUDE.md`
- Câu hỏi gốc: `CLAUDE.md` mục Deploy "CHƯA CHỐT". Sau khi xong #5, cần một môi trường chạy thật để **demo**
  (chưa có khách hàng, chưa có dữ liệu thật). Ba hướng đã cân nhắc: A — PaaS container, B — cloud lớn (AWS/GCP),
  C — VPS tự quản.
- Quyết định: **Hướng A, bản demo miễn phí.**
  - **App:** 1 Web Service trên **Render**, gói **free**, region **singapore**, chạy từ `Dockerfile`, cấu hình bằng
    `render.yaml`. Server Nest phục vụ luôn bản build web → web + API **cùng domain** (cookie `SameSite=Lax`,
    kiểm `Origin` = `APP_BASE_URL`). Health check `GET /api/v1/health` (không chạm DB để Neon được ngủ).
  - **Database:** **Neon** gói free, PostgreSQL 17, region AWS Singapore. App và migration dùng **kết nối trực
    tiếp** (không qua pooler, vì pool gửi `statement_timeout` lúc kết nối) với `sslmode=verify-full`. Mật khẩu role
    `planix_app`/`planix_platform` ≥ 60 bit entropy (yêu cầu của Neon).
  - **Email:** hộp thư bắt email (Mailtrap sandbox) qua cổng **2525** — gói free của Render chặn 25/465/587; email
    không bao giờ tới người thật.
  - **Phát hành:** `autoDeployTrigger: checksPass` — tự deploy khi commit trên `main` có CI xanh.
  - **Migration:** gói free không có `preDeployCommand` → container chạy `db:migrate` rồi mới start server;
    migration giữ **advisory lock** để hai instance chồng nhau lúc deploy không chạy song song.
  - **Quyền owner (security review):** server không đọc, không giữ `DATABASE_URL_OWNER` (owner Neon có `BYPASSRLS`);
    chỉ `db:migrate` và `ops:grant-operator` dùng. Container vẫn nhận biến này để chạy migration lúc khởi động, nhưng
    process server được start bằng `env -u DATABASE_URL_OWNER`. Rủi ro còn lại chấp nhận cho demo: biến vẫn nằm trong
    cấu hình service trên Render; staging thật → chạy migration ở `preDeployCommand` hoặc job riêng và gỡ biến khỏi
    web service.
  - **Proxy:** Render nối thêm (không xoá) `X-Forwarded-For` → `trust proxy` = **số lớp proxy** qua biến
    `TRUST_PROXY_HOPS` (không bao giờ `true`). **Sửa đổi 2026-09-16 (kiểm trên demo, #14):** với `1`, khoá rate limit
    (header `ratelimit-policy` … `pk=`) xoay giữa ~3 giá trị bất kể client gửi gì → đang lấy IP của proxy nội bộ
    Render/Cloudflare, mọi người dùng chung ~3 bucket (một người thử mật khẩu dồn dập khoá đăng nhập của mọi người).
    IP giả không qua mặt được. Đổi thành **`2`**, kiểm lại bằng cùng phép so `pk`.
  - **Operator đầu tiên:** chạy `ops:grant-operator --create` từ máy người vận hành, kết nối thẳng tới Neon, với
    `APP_BASE_URL` = URL demo và SMTP = Mailtrap.
  - **Phát hiện khi chốt:** trên Neon owner không phải superuser → `ALTER ROLE … NOSUPERUSER` trong migration `0001`
    bị từ chối; bỏ `NOSUPERUSER` (role do owner thường tạo không thể là superuser), giữ `NOBYPASSRLS`.
- Giới hạn chấp nhận (chỉ demo): server ngủ sau 15 phút không truy cập, khởi động lại ~1 phút; 512 MB RAM, 0.1 CPU
  (đăng nhập chậm hơn do argon2); rate limit trong bộ nhớ, 1 instance; không cam kết sao lưu.
- Khi cần staging/production thật: đổi `plan` trong `render.yaml`, chuyển migration sang `preDeployCommand`, bật
  không ngủ cho Neon, chọn SMTP gửi thật, xử lý hết #14; cân nhắc lại hướng B/C nếu có yêu cầu vị trí dữ liệu.
- Phương án bị loại (cho demo): gói trả phí Render (chưa cần); Postgres của Render (quyền tạo role chưa kiểm);
  B/C (tốn công dựng và vận hành cho mục đích demo).
